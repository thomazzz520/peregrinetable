# Peregrine Design System

**The governing document for how the dashboard looks, feels, and behaves.**
**Living document. Every future design decision checks against this first. If a decision isn't covered here, add it here, don't decide it silently on one screen.**

---

## How to use this

This is not a style guide of colours and nothing else. It has three layers:

1. **Principles** — the reasoning, so a new decision can be tested against intent
2. **The system** — colour, type, components, voice, the concrete rules
3. **Deep detail per section** — the actual thoughtful, specific reasoning behind each part of the dashboard, added one section at a time as we work through them

Layer 3 is the part that makes the product feel considered rather than templated. It gets built up over time, this document does not need to be finished in one sitting.

---

## 1. Principles

- **Monument Valley is the inspiration, not a skin.** Use it where it earns its place: the office scene, the floor plan, anything spatial. It does not need to be applied to the marketing site, the forms, or the chat interface.
- **Coherent over dark or light.** The brain does not need to be dark specifically. Every part of the product needs to feel like it belongs to the same object. Coherence is the actual rule, dark-vs-light is just one tool for getting there.
- **Sharp shell, soft content.** The frame, nav, and structural chrome stay clean and close to square. Message bubbles, agent chips, and department cards get soft rounding. This split is deliberate, do not flatten it in either direction.
- **One idea, one home.** Every core message (we run on top of what you have, you already pay for this, nothing without approval) lives on exactly one page or one section. If it shows up twice, cut the second one.
- **Show the real thing, don't describe it.** Where possible, a screen proves a claim (an actual morning brief, an actual log entry) rather than a paragraph asserting it.
- **Gamified in feel, serious in function.** The office/department view is allowed to feel like a considered, almost playful space (named agents, department personality, small touches), because a business owner reacting to it should feel "someone actually thought about this," not "this is a generic dashboard template." This only works as long as the functionality underneath is real and useful. Charm without substance reads as a toy. Substance with no charm reads as everyone else's dashboard.
- **Not every new function becomes a new department.** Booking was the first fully workable, deployable system built, and treating it as its own sub-office was the natural first instinct, but as more systems get built over time, every new function needs to be weighed against the same question: does it have enough real, distinct depth to earn its own sub-office, the way Roster's shift drafting and timesheet approval do, or is it one function that belongs as an additional view inside an existing department's page, the way booking folded into Admin. Without this check, the office sprawls into a department per feature instead of staying a small, legible set of real departments. This is an ongoing decision, not a one-time fix, apply it to every new system before it gets built.

## 2. Colour

### Department colour assignment (locked)

This was drifting even within our own work: an early build had Finance as gold and Suppliers as sage-green, a later experiment accidentally swapped them. That drift is exactly why this needs to be written down once, here, as the single source of truth.

**The colour applies to the ground, not the whole department.** In the office view, each department sits on its own floor plate or base, and that plate is where the department colour lives. The desks, figures, cards, and chrome on top of it stay neutral (bone, clay, or white, per Section 4). This is a wayfinding colour, like a floor marking that tells you which zone you're in, not a fill applied to an entire card or component. Getting this wrong (colouring the whole department instead of its ground) is the single easiest way to accidentally make a screen feel loud and childish instead of considered.

- **Finance — gold/amber ground.** The oldest, most legible colour association there is. Money, the books, reconciliation.
- **Suppliers and stock — sage-green ground.** Goods, growth, the physical flow of things coming in.
- **Marketing — soft blue ground.** Reach, communication, the outward-facing side of the business.
- **Roster — dusty rose ground.** People, warmth, the human side of running a floor.
- **Admin — muted teal ground (`#94C0B6`).** The fifth and, for now, last. Teal because it is the one clear gap left in the hue circle between sage-green and blue, so Admin reads as its own zone without crowding either neighbour, and because a cool, quiet, unshowy colour suits the department that holds the supporting functions nobody thinks about until they need them. It carries no other meaning, deliberately: Admin is the place thin functions land, so its ground must not imply anything about which function is currently living there.

Every future screen, chip, chart, or icon representing one of these departments uses its assigned colour as the ground/base tone and no other. **Five departments, five colours, and a sixth is not free.** If one is ever added, its colour gets chosen and logged here before it appears on any screen, and the same test from Section 1 applies first: a new function folds into an existing department unless it has the depth to be its own. A tone per feature is how a coherent set turns into a swatch book.

### The feeling colour is trying to create

Colour is not decoration here, it is doing three separate jobs, and each job should stay recognisable on sight:

- **Department tones (above)** create calm distinction. An owner should be able to tell which part of the business a card belongs to without reading the label, but none of the four tones should compete for attention or feel urgent. They are all equally soft.
- **Sage as an accent** creates urgency, specifically "this needs you." It should be the only colour on a screen that means that, so it never gets diluted by also being used decoratively elsewhere.
- **Navy as an accent** creates weight and structure, "this is the brand, this is a real action." It is calm, not urgent, closer to authority than alarm.

The overall feeling we want a venue owner to come away with is warm, daylight, human, and considered, closer to a well-run local business than an enterprise SaaS product. Cold, high-contrast, heavily saturated colour choices work against that even when they look striking in isolation.

### Background direction

We tested three backgrounds behind the same four department colours: bone (original), navy, and a deeper clay/tan. Bone is coherent but low contrast, colours have to work hard to read. Navy makes colours pop but risks reading cold and techy for a café owner audience. **Deeper clay is the current direction**: still warm and daylight, but with enough contrast that department colours read as intentional rather than washed out. This needs one more pass against a real, dense dashboard screen (not an isolated sample) before it is fully locked in.

### Navy and sage are semantic, not decorative

This is the most important colour rule in the system. Peregrine navy (`#162540`) and sage (`#7fd3b4` / deep sage `#4fae90`) are the brand's two most recognisable colours, and the easiest to overuse. They are reserved for meaning:

- **Navy** marks structure and action: the wordmark, and anything that is genuinely a decision or a command (an approve row, a primary action).
- **Sage** marks attention: a status dot, a ring around something waiting on the owner, an "approve" link. It should consistently mean "this needs you," and nothing else.
- **Neither colour touches the department cards themselves.** The four department tones already do the job of distinguishing sections. If navy or sage is about to be used somewhere that is not structure or attention, it is probably the wrong colour for that spot, reach for a department tone or the background clay instead.

### Hard rule

**No yellow, anywhere, in any form.** Flagged repeatedly across every round of review as the single worst-performing colour choice made so far. Gold (the finance department tone above) is a distinct, muted, deliberately different colour from yellow and is not an exception to this rule.

### The one deliberate exception

**The booking floor plan (Section 10) runs its own separate palette**, mint, coral, stone, a small gold accent, distinct from everything above. This is intentional, not drift, it is justified by the floor plan being presented as its own small, contained diorama, not part of the main app's visual system. Its exact palette is governed by a separate technical document, not this one, see the booking entry in Section 10 for the reasoning and the pointer.

## 3. Layout and shape

The general, product-wide rules for how anything gets composed on a screen, independent of what that screen specifically contains.

- **Everything sits on a base grid.** Use a consistent spacing unit (multiples of 4px) for all gaps, padding, and margins. A gap that is not a multiple of the base unit is a sign something was eyeballed rather than decided, fix it rather than let it stand.
- **Whitespace is generous, but grounded.** Cards and panels get real breathing room around them, but nothing floats naked on the background with no visual anchor. A card sits on a base surface, a section sits inside a clear boundary, even a subtle one.
- **Hierarchy is nested, not flat.** A screen has one clear primary focus, secondary content supports it, tertiary content (fine print, timestamps, metadata) recedes further. If everything on a screen is fighting for the same visual weight, the hierarchy has failed regardless of how good any individual element looks.
- **Function decides layout before style does.** Where something sits on a screen should be answerable by "what does the owner need to see first, and what do they need to act on," not by what looks balanced. Balance is the last pass, not the first decision.
- **No element overlaps another.** This has already happened once in the office view and needs to become a standing rule: resize a section before letting its contents collide.

## 4. Style specifics

The detailed, consistent rules for how individual elements are finished, so nothing feels hand-tuned per screen.

### Corner sharpness, as an actual scale, not a feeling

- **Shell and structure** (the nav bar, the outer frame, the page background): sharp, close to square, 0 to 4px radius at most.
- **Cards and panels** (department cards, message bubbles, agent chip containers): soft, 10 to 12px radius.
- **Buttons and inputs that a person directly acts on** (approve, send, a text field): a small, comfortable radius, noticeably softer than the shell but not as round as a card.
- **Avatars, status dots, pills, and tags:** fully round.
This is the concrete version of the "sharp shell, soft content" principle: the more structural an element is, the sharper it stays, the more a person directly touches or reads it, the softer it gets.

### Shadow

- No drop shadows for decoration. A shadow only appears where it does real work: a focus ring on an active input, a subtle lift on a card that is genuinely elevated above its background (a popup, an active state), never as a default on every card.
- No glow, no blur, no glassmorphism. If a card needs to stand out, use colour or a border, not a soft blur behind it.

### Level of detail

- Icons and small illustrative elements stay simple and flat, not photorealistic, not overly minimalist to the point of being unreadable. Think clean line icons or simple flat shapes, not 3D renders and not single-pixel outlines.
- Department "personality" touches (the chalkboard, the cardboard boxes, the art table) are allowed real character, this is where the gamified feeling lives, but they should still read clearly at a glance, not require close inspection to understand.

### Animation

- Animation is functional, not decorative. It communicates that something happened (a card updating, the brain zooming in when clicked, a status dot changing colour) rather than existing to look impressive.
- No fade-ins as the user scrolls, no cursor-following effects, no hover states that fade a button rather than clearly indicating it is clickable. These are already on the anti-pattern list, restated here because they specifically belong to this section.
- Where motion exists, it should be quick and purposeful, not a lingering flourish. A transition that makes someone wait to understand what happened is worse than no transition at all.

## 5. Function and interaction

How interactive elements behave and where they sit, so the product feels predictable to use even as new screens get added.

- **Round edges mean "you can act on this," square edges mean "this is structure."** This is the functional restatement of the corner rule above: before deciding a shape, ask whether the element is something a person touches and decides on, or something that frames the screen around them.
- **Primary actions are consistent in position.** An approve or confirm action sits in the same relative place across every card and panel that has one (trailing edge, bottom of the card), so a user's hand learns where to look without re-reading the layout each time.
- **One primary action per view.** A screen can have several things to look at, but only one thing that is the obvious next step. If two buttons compete for primary weight, one of them is wrong.
- **Secondary and dismissive actions stay visually quieter** than the primary action, an outline or plain text treatment rather than a filled button, so the hierarchy of "what should I actually do here" stays obvious.
- **Every interactive element gives feedback.** A click, an approval, a toggle should visibly confirm it registered, even if the confirmation is small (a colour change, a checkmark, a status dot flipping). Nothing should leave a person wondering if their action worked.

## 6. Type

- Serif display face for the wordmark and section headers, plain sans for body text and UI chrome.
- No Inter. No Space Grotesk paired with Instrument Serif. No serif italics used as an accent trick on individual words mid-sentence.
- Sentence case for headings and labels, not Title Case, not ALL CAPS (small uppercase micro-labels like section tags are the one deliberate exception, used sparingly).

---

## 7. Components

What each recurring component contains and how it behaves. See Section 4 for corner radius, shadow, and finish rules that apply to all of these.

- **Nav bar:** the real logo mark top left, primary nav items, one clear call to action on the right.
- **Department cards:** neutral card chrome, sitting on that department's coloured ground/base plate (Section 2), a title, one or two live stats, a status indicator if something in that department needs attention. Never overlapping another card, resize the section before adding more cards.
- **Agent chips:** name, job title, a presence dot (green = fine, sage = needs attention, current direction, still being tested, never yellow), a small square badge showing the actual source of the data that agent works from (for example a Xero mark on an agent handling the books), no fully human face, Bitmoji-simple heads at most in flat 2D contexts, full-bodied in the 3D office view (Section 10). The data-source badge exists so the "we connect what you run, we don't replace it" positioning is visible at the agent level, not just claimed in marketing copy.
- **Approval actions:** every agent output that can act ends in two buttons (approve / not now), never information alone with no way to act on it.
- **The morning brief pattern:** a long, specific, satisfying "handled overnight" list next to a short, ruthless "needs you" list. The length contrast between the two is the actual point, do not let either side drift toward the other.
- **No coloured left-border cards, no glassmorphism, no untouched default component-library styling.** If a component came from a library, it should not look like it.

---

## 8. Voice and copy

- No em dash, anywhere, in any document or on-screen copy.
- Plain, owner-facing language. Not "TOGETHER WE REINVENTED," more "you run the business, Peregrine runs the software."
- Say the strongest line once. Do not restate it elsewhere for reassurance, that reads as insecure rather than confident.
- No generic buzzword copy ("leverage," "seamless," "unlock," "empower").
- Modelled examples get labelled as modelled. Never let a screen imply an exact result happens identically every day.

---

## 9. The anti-pattern checklist

If a screen has any of these, it reads as AI-generated by default, regardless of how good the underlying idea is. Check every new screen against this list before calling it done.

**Colour and background**
- Purple-to-blue gradient
- Gradient hero text
- Low-contrast dark mode
- Grain texture over a gradient

**Type and copy**
- Inter font everywhere
- Space Grotesk plus Instrument Serif
- Serif italics for accent words
- Generic buzzword copy
- Em dashes everywhere

**Layout and components**
- Three icon boxes in a row
- A badge above the headline
- Coloured left-border cards
- Glassmorphism cards
- Untouched shadcn components
- Inconsistent spacing

**Icons and motion**
- Emojis in headings
- Lucide icons everywhere
- Sections fading in as you scroll
- A beam that follows your cursor
- Hover effects that make buttons fade

## 10. Deep detail per section

This is where the real thinking lives, added one section at a time. Each entry should explain not just what a section looks like, but why, in enough detail that someone reading it understands the reasoning well enough to extend it consistently.

### Product shell (the logged-in nav and header)
*Status: partially locked, two items below need a real decision before they get built.*

**This is the persistent chrome around the actual product, not the marketing site.** The office view, the morning brief, and the brain all sit inside this shell. It is a separate thing from the marketing site's nav (Section 10, marketing site entry), which is outward-facing and built to get a visitor to book a session. This shell is what a client lives inside daily, once they already are one, and the two should never borrow items from each other.

**The header shows the client's own business, not Peregrine's brand.** The primary wordmark in the header is the client's business name, with their trade and suburb underneath as a subtitle, for example "The Peacock," "Jenny's Café, South Yarra." An owner opening their dashboard should see their own business looking back at them, not Peregrine's logo pushed at them. This is the "you run the business, Peregrine runs the software" principle made real at the exact moment someone logs in, without saying it out loud, the same kind of implicit reinforcement as the morning brief's headline tone (Section 10, morning brief entry).

**Nav items are functional, not persuasive.** Revenue, History log, Contact.

- **History log** is the fuller expression of the record-of-actions idea already established for the morning brief, a real, browsable record lives here, not just the short per-item reasoning trails shown on the brief itself. The brief shows the trail behind one specific item, this shows everything.
- **Revenue is not yet defined.** It appears in the nav but has no locked content decision behind it anywhere in this document. Do not build it from assumption, decide what it actually shows first, then write that decision here.
- **Contact, inside the product, is very likely a different surface from the marketing site's Contact page**, one is a support or reach-Peregrine path for an existing client, the other is a lead-qualifying form for a prospective one. Confirm this rather than assuming the two share a form or a destination, they should not by default.

**What this is not:** it does not contain any marketing-site item, Platform, About us, or Book a demo have no place here, those exist to convince someone to become a client, this shell exists for someone who already is one.

**Acceptance checks.** Run these before calling the shell finished.

1. Does the header show the client's own business name, or does it show Peregrine's? It must show the client's.
2. Does the nav contain any marketing-site item (Platform, About us, Book a demo)? Any of those present is a fail.
3. Open History log. Does it show a genuine, full, browsable record, not just the short per-item trails already shown on the morning brief? It should go deeper than the brief, not repeat it.
4. Ask directly: does Revenue have an actual, written content decision behind it yet? If the answer is no, it is not ready to be built, flag it rather than guessing.

### Office / department view
*Status: locked.*

**Structure. The number of floor plates is not fixed at four, it grows with the business.** Every current department (Finance, Marketing, Suppliers and stock, Roster, Admin) gets a plate, and a new plate gets added whenever a genuinely new department is warranted (Section 1, not every new function becomes a new department). This view has to be designed to scale outward, not treated as a fixed layout. Each plate carries its department's ground colour (Section 2). Everything on top of the plate, the desks, the figures, the card, stays neutral. This is the one rule most likely to get broken by accident, colouring a whole card instead of its ground, so it is worth checking on every new department screen specifically.

**Each department gets one physical prop set, not shared generic furniture.** Finance gets a desk and a calculator. Marketing gets a small art table. Suppliers and stock gets a stack of boxes and a truck. Roster gets a chalkboard. This is where the "gamified but serious" principle earns its place: the prop set is what makes a department recognisable at a glance and gives the space personality, but it is furniture, not a game board, it should read as "someone thought about this desk" not "welcome to a level."

**Figures are full-bodied and animated, not static blobs.** They have legs, they walk between desks, they sit, they work, the way a real small office looks from above. This is a correction from an earlier draft of this section, which assumed simplified, legless figures to avoid an uncanny effect, that reasoning does not hold once figures are rendered at this level of polish and stylisation (see the level of detail standard below), a well-made stylised character with a body reads as alive and considered, not unsettling. What stays true from the earlier draft: each named agent still needs a distinct, individually recognisable head, that part of the reasoning holds regardless of how the body is built.

**Level of detail is a genuine production standard, not a placeholder.** Because the view can be zoomed in fully, every asset needs to hold up at close range: real desk geometry (not a flat box), proper chairs, cubicle partitions, filing cabinets, plants, a break area with tables and chairs, characters with believable proportions and actual movement. The reference standard for this is a polished isometric office-sim look, stylised and low-poly, not photorealistic, but crafted with real depth and variety in every asset, the way a shipped game environment looks rather than a wireframe mockup. Colour palette does not follow this reference (Section 2 governs colour), only the depth and craft of the modelling and the sense of a space that is actually lived in.

**The card sitting on each plate shows exactly two or three live numbers, never a full report.** For example Finance shows reconciled-to-date and payrun status, not a breakdown of every line item. The card's job is "is this department fine or not," not "here is everything." Anything deeper belongs in the brain chat, which is built for depth, this view is built for a glance.

**A status indicator only appears if something in that department needs the owner.** No status indicator, no visible flag, means genuinely nothing to look at, not "green means fine." Absence of a signal is itself the signal. This keeps the view calm most of the time, which is what makes the moments something does need attention actually stand out.

**Cards never overlap.** If a new department or a new stat causes a collision, the fix is resizing the section (Section 3, layout and shape), never letting cards sit on top of each other. This has happened once already in review and is the most common failure mode of this view as it grows.

**Clicking a department opens a full page for that department, not a small popup, and that page carries its own internal navigation bar.** This is a correction from an earlier draft of this section, which described the click behaviour as a small read-only popup, it is a proper page with real function inside it, not a glance-and-close overlay.

**Admin, specifically, is the department for supporting and cross-cutting functions that are each too thin to be their own sub-office.** Booking lives there as one view in Admin's page, alongside enquiries and calls, and future thin functions (legal and compliance tracking is the next likely example) are expected to fold in the same way, as another view inside Admin's page, rather than each spinning up as a new sub-office. This is the concrete, ongoing application of the growth principle in Section 1, Admin is deliberately built to be the place new, single-function additions land by default, until one of them grows enough real distinct depth to justify becoming its own department.

**What this view is not:** it is not where an owner chats with or negotiates with an agent, that stays in the brain (Section 10, next entry). A sub-office page is for viewing and directly managing real operational data, the runsheet, a call log, a booking's seating. The brain is for depth, conversation, and approving what an agent has drafted. Both are real, active surfaces now, the distinction is what each one is for, not which one allows interaction.

**Acceptance checks.** Run these against a screenshot before calling any office screen finished.

1. Does colour sit only on the ground plate, never on the card, desk, or figure above it? Colour anywhere else is a fail.
2. Do any two department cards overlap on screen? Any overlap is a fail, resize the section.
3. Do the figures have full bodies and visible legs, not static legless shapes?
4. Zoom in on one desk or prop. Does it hold up at close range, or does it read as a placeholder box? Close inspection is the actual test, this view is built to be zoomed into.
5. Is a status indicator showing on a department with nothing to report? There should not be one, absence is the signal.
6. Could a new department be added to this layout without a full redesign? If not, the structure has failed the scaling principle in Section 1.

### The brain and department chat
*Status: mostly locked, one open experiment noted below.*

**Structure. A constellation of floating knowledge nodes, no central object, the whole thing floats freely in the air above the centre of the venue,** it does not sit resting on a plate or a base the way the department cards do. There is no ball, no core shape sitting in the middle, the density of nodes itself is the centre. This is a deliberate expression of the actual product idea: Peregrine does not replace what a venue runs, it connects and learns from it, a single glowing core would visually contradict that by suggesting one contained brain rather than a growing network across everything the business already uses. The connections between nodes are thin lines, never thick, this stays a delicate web, not a bold diagram.

**Density grows with time, and that growth is the point, not a decoration.** More days with a venue means a visibly denser, more connected constellation. This is the compounding-context moat made literal, an owner should be able to see, not just be told, that the system knows their business better the longer they stay. A brain that looks the same on day one and day two hundred has failed at its one job.

**The shape is circular and interconnected, not a tree.** Nodes from different departments genuinely link to each other, because departments in a real business are not siloed, a supplier price change affects finance, a booking affects roster. These cross-department links render in navy, not sage, quiet and structural, they are showing the product's actual architecture (everything connected), not flagging something that needs attention.

**Nodes take their colour from the department they represent, using the same ground colours locked in Section 2, kept pastel.** A finance-related node is a soft gold, not a saturated one, a roster-related node is a soft rose, and so on, matching how those tones already behave everywhere else. This is what makes the brain and the office view feel like one coherent object instead of two different visual systems that happen to share a name.

**Clicking near the centre triggers a zoom-in, then the chat opens, it is never instant.** The motion is functional (Section 4), it communicates "you are moving into the intelligence," not decoration for its own sake. An instant cut here would undersell the moment this is meant to be.

**Two levels of chat live inside here, and they are reached differently.** Clicking into a department opens a page about that department: a roster of its named agents and what each one currently handles, for example Sarah on the books, Lara checking the tills, Brett working out tax. Clicking on any one of those agents shows their individual status, an issue they are facing, or plainly that there is nothing to report, and opens a one-to-one chat with that agent specifically. Separately, clicking directly into the centre brain opens a chat with the whole department at once, one conversation addressed to the team rather than a single person. Both exist because both are real needs, sometimes an owner wants to ask one specific person a question, sometimes they want the department's overall picture.

**Every department includes one checker, a named person whose only job is verifying the other agents' work before it reaches the owner.** This exists so approving something never means trusting it blindly.

**Presence dots: quiet green means fine, sage means needs attention.** This is the current direction, not fully settled, worth testing against a real, busy screen before it is locked for good, since sage is also carrying meaning elsewhere and it is worth confirming the two uses do not start to blur once there is more happening on screen at once.

**If any agent in a department needs attention, opening that department's page leads with a short, time-aware greeting** ("Good morning, here's what needs you") before anything else. This is one of the only places in the whole product where the interface speaks first rather than waiting to be asked, reserved for exactly this moment so it stays meaningful.

**Every agent reply, individual or whole-department, ends in two buttons, never information alone.** This is where the product's core promise, act rather than advise, is literally executed. A reply that only states a fact without an approve/dismiss action attached is not finished.

**What this is not:** it is not where an owner gets a spatial, at-a-glance read of the business, that is the office view. The brain and its chat are for depth and for action, going here should feel like a deliberate step in, not a passive glance.

**Acceptance checks.** Run these against a screenshot or a click-through before calling the brain finished.

1. Is there a solid object or ball at the centre? There should not be, node density is the centre.
2. Do node connections render as thick lines anywhere? They should be thin throughout.
3. Pick two cross-department links. Are they navy? Sage on a structural link is a fail, sage is reserved for attention only.
4. Click into one department, then into one named agent, does a one-to-one chat open? Then click the centre directly, does a whole-department chat open? Both must exist and be distinct.
5. Is any "needs attention" indicator yellow or amber anywhere? It must be sage, always.
6. Pick any agent reply. Does it end in two buttons? A reply with only information and no action attached is unfinished.

### Booking (inside Admin)
*Status: locked, pending your confirmation on the merge itself.*

**Booking is not its own sub-office, it lives inside Admin's page as one of its selectable views.** It was originally treated as a standalone department, that overweighted what is really a single function, a runsheet, alongside a floor plan. Admin already covers the adjacent front-of-house work, calls, enquiries, booking naturally sits with them, they are all "the phone and the door." Roster was considered for a similar merge and rejected, it has enough real distinct depth, shift drafting and timesheet approval, to justify staying its own sub-office.

**A new booking shows as a small notification in the bottom-right corner, visible for a few seconds, only while the owner is logged in and actively on the dashboard.** If a booking arrives while they are offline, nothing pops, it is not stored as a missed alert to catch up on individually, it simply accumulates. Next login shows a plain summary instead, "you have 5 bookings," rather than replaying five individual notifications after the fact.

**Two views exist inside the runsheet page, and the plain runsheet is the default, always.** It matches what an owner already keeps on paper, print and check, nothing new to learn. The second view is a visual floor plan, using Monument Valley's style specifically, this is one of the few places that style fully applies (Section 1), because it is meant for a guest booking a table, not for daily internal use.

**The floor plan's exact visual execution is governed by a separate, more technical document Jason wrote** (`.claude/rules/art-direction.md` in the peregrinetable repo), that document is the source of truth for the scene's camera, materials, and palette, this entry only covers what a product decision-maker needs to know, not the underlying code. Two things from it are worth stating here directly, because they are product decisions, not just implementation detail:

- **Booking state reads as depth, not a colour legend.** An available table sits in full colour and full contrast, a fully booked table desaturates and flattens, visually receding, the way distant buildings fade in the reference art style. A guest or owner should feel which tables are open without reading a key. This is a sharper version of "the booking system feeds the floor plan directly," stated above, worth remembering as the actual mechanism.
- **The floor plan is deliberately its own small, contained world, presented inside a frame, like a model of the venue held in a case, not a map.** Because of that framing, it uses its own separate palette (soft mint, coral, warm stone, a small gold accent), distinct from Peregrine's main navy and sage system. This is an intentional exception, not drift, the containment (the frame, the case metaphor) is exactly what justifies a self-contained palette. If the floor plan ever stops being presented as a contained diorama, this exception needs to be revisited.

**The owner is asked which view they want to use day to day, never defaulted into the fancier one.** The floor plan stays available as an option, and remains what a customer sees when making a booking regardless of which view the owner personally prefers.

**The booking system feeds the floor plan directly, they are the same data, shown two ways, not two separate systems that need to agree with each other.**

**Seat allocation defaults to one rule: a booking for a given party size is only offered a table matched to that size, never a bigger one, until every table of the correct size is full.** This is the default behaviour, not an unchangeable constraint, an operator can manually override a specific allocation if they choose to. What does not happen automatically is a table getting quietly reshuffled after a guest has already booked it, any change happens because a person decided to make it, not because the system rearranged things on its own.

**The runsheet has a working print function.** Some owners will always want a paper copy on the pass or by the till, this is not a nice-to-have, it needs to actually work.

**What this is not:** it is not a place where the owner is required to learn a new visual language just to see tonight's bookings. The runsheet exists specifically so nothing changes for them by default, the floor plan is the upgrade they can choose into, never the thing they are stuck with.

**Acceptance checks.** Run these before calling the booking experience finished.

1. Is booking reachable as its own top-level tab? It should not be, it lives inside Admin's page only.
2. Does booking's card in the office view carry a department ground colour? It should not, it stays neutral with an "ours" tag.
3. Open the booking view fresh. Is the runsheet showing by default, ahead of the floor plan? It must be.
4. Try to reassign a seat mismatch. Does it happen silently, or does it require a deliberate operator action? It must require deliberate action.
5. Look at an available table and a fully booked table side by side on the floor plan. Does the booked one visibly recede, desaturated and flatter, without needing a legend to explain it?
6. Simulate a booking arriving while offline, then log in. Does it show as one accumulated summary, not a replay of an old notification?

### Morning brief / needs-you panel
*Status: locked.*

**This is a persistent panel, always visible, not a page an owner navigates to or a popup they open.** It sits alongside the office view rather than replacing it, this is meant to be the first thing seen, not something found. An owner opening the dashboard should not have to go looking for whether anything needs them.

**As the owner scrolls down into the office view itself, this panel and anything similar sitting near the top (a weather widget, for example) tuck away rather than staying pinned.** The brief is the entry point, but once attention has genuinely moved to the office and its agents, the interface should get out of the way rather than compete for space. It reappears when scrolled back up.

**The contrast between the two lists is the entire mechanic, not a formatting choice.** One side is long, specific, and satisfying, a real list of what got handled overnight (card takings matched to Xero, supplier prices checked, calls answered, a roster drafted), each with a real number attached. The other side is short and ruthless, ideally one or two items, never padded to look busier than it is. The length difference is the actual pitch, "look how much happened, and how little is actually left for you," if either side drifts toward the other this stops working.

**Every item in the handled-overnight list names the specific agent who did it and what they're responsible for**, not a generic "the system." Card takings matched to Xero, next to Sarah's name and her role on the books, not a faceless line item. This is the same reasoning as the data-source badge (Section 7), applied to this list specifically, it keeps the "real named people are doing this work" idea consistent everywhere it could otherwise quietly disappear into a plain list.

**A headline states the count plainly** ("two things need you") **with a one-line summary underneath** (watched so many, handled so many, everything else resolved on its own). **This line has a second job beyond information: it should make the owner feel, without ever stating it outright, "you are still the one running this, and you were helped enormously while you were away."** Not "Peregrine handled your night" (that centres the product), and not a dry count with no warmth (that centres nothing). The number and the tone together should land closer to a good second-in-command reporting back to the person actually in charge, engaging and a little proud of the work, never robotic, never taking credit out loud.

**The panel carries a real as-of time** ("06:04, the morning brief"), it is presented as work completed and ready before the venue opens, not as a live feed updating in front of the owner. This reinforces the actual story, the work happened while they were closed, they are reading a finished brief, not watching something happen.

**Every needs-you item carries its own short reasoning trail, not a separate page.** A price check, a redraft, then the item waiting for approval, three or four short timestamped lines is enough. This is where the earlier idea of a big, standalone "trace any figure back to its source" section actually lives now, in miniature, attached to the one item it explains, rather than as its own grand claim elsewhere in the product.

**Every item ends in an approve or dismiss action** (Section 7, Section 10's brain entry), and resolving it here removes it from this panel and from the brain's own attention greeting at the same time, they draw from the same underlying queue, not two lists that happen to look similar. An item resolved in one place and still showing in the other is a bug, not a style choice.

**When nothing needs the owner, the panel says so plainly and calmly, it does not go blank, and it still has something in it.** The same principle behind the office view's quiet status dots applies to the headline itself, absence of something to approve is good news and should read that way. But the space below should not sit empty either, it holds one small, genuinely positive highlight instead, a best-seller, a strong night's number, something worth a glance even though there is nothing to act on. Calm and empty are not the same thing, this state should feel like good news, not like the panel has nothing to say.

**Any specific, impressive example shown here (a precise price jump, an exact quote value) is a modelled example and should be labelled as one where it appears in marketing or a demo** (Section 8). This is the component most likely to overpromise, because a strong worked example is genuinely persuasive, the discipline is making sure it never implies that exact output happens identically every single day.

**What this is not:** it is not a place for back-and-forth conversation, that is the brain. This panel states a fact, shows the short trail behind it, and offers an action, it does not open into a chat. If an owner wants to ask a follow-up question about an item, that is a deliberate step into the brain, not something this panel tries to handle itself.

**Acceptance checks.** Run these before calling the panel finished.

1. Scroll down into the office view. Does the panel tuck away, or stay pinned in place? It should tuck away.
2. Pick any handled-overnight item. Does it name a specific agent? It should never read as a generic "the system did this."
3. Resolve a needs-you item from this panel. Does it also disappear from the brain's greeting? It must, both draw from one queue.
4. Read the headline aloud. Does it sound like a proud second-in-command reporting back, or does it sound like the product taking credit, or like a cold count with no warmth? Only the first is a pass.
5. Clear every needs-you item. Does the panel go blank, or does it still hold one small positive highlight? It must hold something.
6. Find a specific, impressive number in the brief. Is it labelled as modelled wherever it appears in marketing? It must be.

### Marketing site (landing, platform, about, contact)
